STEP 02

前端 V1 实现 + 定义 i18n Key

开发根据设计稿实现页面，定义 i18n key 命名并生成初始英文 JSON 文件

Developer — 负责执行 Designer — 确认对齐

Key 命名规范

i18n key 是前端架构的一部分，命名应与组件结构对应，遵循以下约定：

规则示例
命名空间为项目名（camelCase）goldenSeason
Key 使用 camelCaseheroTitle   ✗ hero-title
按组件/功能区域分组holdToEarn, holdToEarnDesc
操作用动词开头joinNow, trackMyRewards, depositUsdt
状态用形容词/过去分词active, ended, claimed
FAQ 以 faq 为前缀faqWhoIsEligible, faqWhoIsEligibleAnswer
错误/提示以类型为前缀enrollmentFailed, loadFailed

操作步骤

1

实现前端页面第一版

根据设计稿搭建页面结构，将所有用户可见文案提取为 i18n key 引用。

2

生成初始 i18n JSON 文件

将所有 key 和英文值整理为标准 JSON 格式，放在项目的 locale 目录下。

● en.json — 初始 i18n 文件示例 
{
  "goldenSeason": {
    // Hero Section
    "badge": "New Listing",
    "heroTitle": "imToken x Tether",
    "heroSubtitle": "Gold Grand Giveaway",
    "earnUpTo": "Earn up to",
    "apy": "50% APY",
    "joinNow": "JOIN NOW",

    // Campaign Phases
    "holdToEarn": "Hold to Earn",
    "holdToEarnDesc": "Hold any amount of USDT...",
    "tradeToEarn": "Swap to Earn",
    "spendToEarn": "Spend to Earn",

    // Long HTML content (code-managed)
    "holdToEarnRewardsDesc": "Hold any amount...<br /><b>1. Entry...</b>"
  }
}
3

区分 Figma 管理 vs Code 管理的 key

在代码注释中标注哪些 key 由 Figma Variables 管理（短文案），哪些由代码直接管理（长 HTML 文本）。这决定了设计师在 Step 03 需要导入哪些 key。

● key 分类标注 
// ═══ Figma-managed keys (短文案，设计师通过 Variable 管理) ═══
"badge": "New Listing",           // ← 进入 Figma Variables
"heroTitle": "imToken x Tether",   // ← 进入 Figma Variables
"joinNow": "JOIN NOW",             // ← 进入 Figma Variables

// ═══ Code-managed keys (长文本/HTML，开发侧维护) ═══
"holdToEarnRewardsDesc": "...",    // ← 不进入 Figma
"faqRewardsLimitAnswer": "...",    // ← 不进入 Figma
4

与设计师对齐 Key 命名

将 i18n 文件提交 PR 后，邀请设计师 Review。确认 key 命名能被理解，且所有设计稿中的文案都有对应 key。

协作要点：开发不需要等文案 100% 确定才开始。只要设计稿有 80% 的英文文案，就可以开始 V1 实现。后续文案修改通过 Figma Variable 导出 → PR 的方式增量更新。

➤ 本步骤产出物

1. 前端页面 V1（代码已使用 i18n key 引用）

2. en.json 初始 i18n 文件（已提交 GitHub）

3. Key 分类清单（哪些进 Figma，哪些 code-managed）
