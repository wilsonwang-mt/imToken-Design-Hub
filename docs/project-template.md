# 项目模板：每个项目至少包含什么

一个项目在站点上由四部分组成，数据都写在 `content/projects/<slug>/project.ts`（字段定义在 `content/projects/_schema.ts`）：

| 部分 | 出现在哪 | 作用 |
|---|---|---|
| 项目卡片 | `/projects/` 列表 | 一眼看懂这是什么项目、到哪了 |
| 概览页 | `/projects/<slug>/` | 没参与过的人 1 分钟内看懂：为什么做、到哪了、定了什么、还有什么没定 |
| 材料 | `/projects/<slug>/<key>/` | 方案、调研、会议记录、原型……每份一个子页面 |
| 外部链接 | 概览页「项目信息」 | Figma、Drive、PRD 等站外资料 |

用 `npm run new:project` 生成后，所有要填的地方都标了【待填写】，填完 `npm run check` 才会通过。

## 1. 项目卡片

| 字段 | 必填 | 写法 | 例子 |
|---|---|---|---|
| `title` | ✓ | 项目名，≤16 字 | Swap 改版 |
| `en` | ✓ | 英文名或英文副标题，≤40 字符 | Swap Redesign |
| `status` | ✓ | 卡片上的状态，阶段 + 版本或节点 | 设计中 · v0.2 |
| `phase` | ✓ | 当前在做的事，≤24 字 | 竞品调研 · 流程原型 |
| `desc` | ✓ | 40–120 字：要解决什么问题、给谁用、现在到哪一步 | 重做 App 内的兑换流程：减少确认步骤，把滑点、手续费和路由讲清楚。目前完成竞品调研，正在做流程原型，下周评审。 |
| `tags` | ✓ | 1–5 个，产品模块或工作类型 | Swap、交易、流程 |
| `stats` | ✓ | 空数组 `[]`，或恰好 3 项有说服力的数字 | 12 · 访谈用户 |
| `stage` | ✓ | 7 个值之一，决定概览页状态标签的颜色；卡片上显示的文字写在 `status` 里 | `exploring` 探索中 / `designing` 设计中 / `reviewing` 评审中 / `building` 开发中 / `shipped` 已发布 / `paused` 已暂停 / `archived` 已归档 |
| `owner` | ✓ | 负责人名字 + 职能，可加 GitHub 账号 | `{ name: 'Alice', role: '产品设计', github: 'alice' }` |
| `members` | | 其他参与者，同样只写名字和职能 | 交易产品、前端开发 |
| `updated` | ✓ | 最近一次更新的日期，等于 `changelog` 第一条 | 2026-10-13 |

人员只写名字和职能（产品设计、视觉设计、交易产品……），不写头衔、级别或汇报关系。

## 2. 概览页

概览页由 `<ProjectOverview>` 按固定顺序渲染，区块的顺序和锚点（`#background` 等）全站一致，审稿人和同事可以直接跳到某一块。

| 顺序 | 区块 | 来源字段 | 至少写什么 |
|---|---|---|---|
| 1 | 标题区 | 卡片字段 + `docs` | 自动生成：阶段、负责人、更新日期、材料切换 |
| 2 | 背景与目标 `#background` | `overview.background`、`overview.goals` | 为什么做：问题和背景，2–4 句。目标：1–5 条，能判断做没做到（如「确认页放弃率下降 20%」），不写「提升体验」 |
| 3 | 当前状态 `#status` | `overview.current`、`overview.timeline` | 一句话说现在到哪了；时间线写已完成、正在做和下一个节点（`done` / `now` / `next`） |
| 4 | 项目特有内容 | 页面里的 children | 可选：这个项目独有、放不进固定区块的内容 |
| 5 | 材料 `#materials` | `docs` | 自动生成：每份材料的类型、状态、日期、一句话结论 |
| 6 | 关键决定 `#decisions` | `overview.decisions` | 已经定下的事，带日期，最新在前。会议里定的事要同步到这里 |
| 7 | 待决问题 `#questions` | `overview.openQuestions` | 还没定的事，写清楚由谁回答 |
| 8 | 项目信息 `#people` `#links` `#changelog` | `owner`、`members`、`links`、`changelog` | 负责人与参与者；外部链接（需要公司账号的标 `needsLogin`）；更新记录 |

还没有内容的区块写空数组，页面会显示「还没有……」，不要删掉区块。

## 3. 材料

每份材料在 `docs` 里登记一条，`npm run new:doc` 会自动加好：

| 字段 | 写法 |
|---|---|
| `key` | 网址的一段，小写英文和连字符：`/projects/<slug>/<key>/` |
| `title` | 材料标题，如「竞品调研」「10/12 评审会」 |
| `type` | 材料类型，见下表 |
| `kind` | `page`：站内页面（用 `<ProjectDoc>`，正文按站点样式写）；`hosted`：托管整页（原型、Claude 生成的长文 HTML，放在 `public/projects/<slug>/<key>/index.html`，多页原型可以有子目录） |
| `status` | `draft` 讨论稿 / `final` 定稿 / `archived` 已归档 |
| `date` | 最近更新日期 |
| `author` | 作者名字 |
| `summary` | **一句话结论**，不是介绍。写「5 家竞品都把费用放在确认前一屏」，不写「本文调研了 5 家竞品」 |

每类材料至少包含这些内容：

| 类型 | `type` | 至少包含 |
|---|---|---|
| 方案提案 | `proposal` | 背景与问题；方案（多个方案时写清取舍）；推荐方案和理由；需要谁在什么时候决定什么；风险和依赖 |
| 会议记录 | `meeting` | 日期、参会人；议题；结论（定了什么）；待办（负责人 + 时间）；没定的问题。结论同步到概览页的「关键决定」 |
| 调研 | `research` | 要回答的问题；方法和样本（来源、时间、数量）；发现（每条有证据或来源）；对设计的启示；局限 |
| 设计规范 | `spec` | 适用范围；组件或规则清单；状态和边界情况；和开发的对接（Figma 链接、token）；变更记录 |
| 原型 | `prototype` | 要验证什么；怎么操作（入口和主路径）；对应的设计稿版本；已知限制 |
| 评审记录 | `review` | 评审对象和版本；评审人；问题清单（严重程度 + 结论）；跟进状态 |
| 传播物料 | `comms` | 目标受众和渠道；核心信息；物料清单和状态；合规、法务确认情况 |

托管整页适合原型、交互演示和 Claude 生成的长文，但要遵守 [style-guide.md](style-guide.md) 的「托管整页」约定；能用站内页面写的材料优先用站内页面，视觉才会和站点一致。

## 4. 维护

- **每次推进**：改 `updated`，在 `changelog` 最前面加一条（日期、谁、做了什么）；`status`、`phase`、`overview.current`、时间线同步更新。
- **阶段变化**：同时改 `stage` 和 `status`。暂停的项目改成 `paused`，并在 `overview.current` 写明原因和恢复条件。
- **结束**：上线后改成 `shipped`，补上结果（数据、链接）；不再维护的项目改成 `archived`，页面保留。
- **材料定稿**：`status` 改成 `final`；被取代的材料改成 `archived`，不要删除，概览页的链接会保留。
