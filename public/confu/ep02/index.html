RECAP 01 · 从零出画布

回顾：让 AI 少猜，靠的是一份写全的 Brief

刚才看到的1Brief 先写好，agent 只负责翻译成画布2画布上直接改字、切 Tweak3一份设计按使用者拆成三种交付
✕ 常见写法AI 只能猜

帮我给「我是主理人」活动做一个好看的官网，风格现代一点，要有科技感。

✓ 更专业的写法 · Brief 骨架
角色你是资深产品设计师兼前端工程师，用 Claude Design 产出「我是主理人」活动官网的可交互画布。
口径以 All Hands deck 第 07–25 页为准：这不是黑客松，是主理人选拔。
输入deck 全文、现站走查 27 条、imToken Web DS 的 token。三者冲突时以 deck 为准。
不可妥协文案逐字来自 deck，不许润色；首页十一段顺序固定，不许增删；没定的日期留空；颜色、字号、圆角只用 DS token；禁止 emoji 图标、渐变铺底、左侧色条卡片。
规格三个画板：桌面 1440 可交互整站、手机 390、主视觉 1920×1080。每段按「段落 | 现站状态 | 你要做的」写成表格。
验收1440 和 390 各截图，逐项点交互，console 零报错，然后再发布。
回报链接；每段做了什么；哪些是示例或假设；和 Brief 不一致的地方。

一份 Brief 要写全这五样

  • 口径：以哪份文档为准，冲突时听谁的
  • 文案：逐字给出，不让它自己写
  • 视觉规则：token、唯一的突破点、禁止项
  • 结构：段落顺序写死，不许增删
  • 验收：截图宽度、要点的交互、console

在 Claude Design 里这样改

  • 大方向在对话里改；某个组件用行内评论；改字、挪位置直接在画布上动
  • 反馈要能执行：「表单字段间距收到 8px」比「看起来不太对」有用
  • 换方向之前，先让它把当前版本存下来
  • 只把贯穿全站的变量做成 Tweak，比如强调色；文案写死在页面里

RECAP 02 · 设计交给工程

回顾：规则写成 Primer 反复用，交出去之前先让它自审

刚才看到的1一份 Primer 贴在每个对话最前面2它自己点出 18 条问题和一个待决冲突3导出时附上数据接口说明
✕ 常见写法AI 只能猜

做一个世界杯预测产品的首页，深色，有科技感，要高级。

✓ 更专业的写法 · Primer + 单屏需求
产品WC2026 HyperAgent：只面向 imToken 老用户的封闭社区赛。AI 找出定价偏差的市场并解释理由；Polymarket 结算，每一笔都由用户自己签名。
要像Linear 的专注和密度、Apple Sports 的赛程卡片、Polymarket 的交易场感。
不要像DraftKings 式的赌场感和假紧迫感；霓虹赛博朋克；满屏彩虹渐变。
Token语义命名，浅色、深色各一套：--bg、--card、--ink、--brand（#007FFF）、--yes、--no。组件里不写死色值。
响应式手机优先，390、平板到 1440 都要顺畅可用。
本屏Match 详情和 AI 对话：连接钱包、AI 判断、下注预览、签名状态，都以卡片形式嵌在对话里。
交付4 个变体：mobile-light、mobile-dark、desktop-light、desktop-dark。

一份 Primer 要写全这五样

  • 产品和受众：一句话说清给谁用、解决什么
  • 正反参照：要像谁、不要像谁，各 3–5 个，比形容词准
  • 语义 token：双主题，按用途命名，不按颜色命名
  • 字体、动效、响应式：写成数值，不写感觉
  • 升级时写明覆盖哪一条：例如 Visual Refresh 注明覆盖 v2 §4

交给工程之前

  • 先让它自审：每页在浅色、深色、桌面、手机下都实际点一遍（按钮复制这段 Prompt）
  • 让它写数据接口说明：字段名就用前端现在绑定的名字
  • 导出前清掉没被引用的旧文件；交给对方时附一句「先读 README 和接口说明」
  • 有代码库的团队，可以在 Claude Code 里用 /design-sync 把真实组件和 token 同步进 Claude Design

工具的限制 · 2026-09 预览版
  • 画板之间状态不共享，桌面和手机的交互各管各的
  • PNG、PDF 导出不嵌 Google Fonts，中文会回退成系统字体
  • 画布文件不能直接分发，要先转成独立 HTML
  • 两人同时编辑会冲突，适合一人主编
它会犯的错
  • 自信地写错：示例数据、猜的日期，写得和事实一样
  • 热心地补充：加上你没要的段落、动效和颜色
  • 规则冲突时自己挑一个：项目 2 的 Primer 和设计系统打架，它先按自己的判断做，审计时才列出来
  • 越改越偏：改到第五轮，颜色悄悄多了两种
必须你来做的
  • 判断这个页面到底要讲什么
  • 在几个都画得出来的方向里选一个
  • 决定哪些地方不改，并说得出理由
  • 没定的信息留空，不让它编
  • 品牌资产宁可绕路去拿原图，也不让它重画
什么时候别用它 正式物料、高清导出 → Figma 要直接上线的代码 → Claude Code 多人同时编辑 → Figma

明天就能用的起手 Prompt：七段结构

三个项目的 Prompt 长短不一，结构都是这七段。第 ⑤ 段最长，也最值得花时间。

①角色你是谁
②背景这件事是什么、给谁看、以哪份文档为准
③输入你会拿到什么，冲突时以谁为准
④不可妥协3–6 条硬规则
⑤规格逐屏写，用表格，不用段落
⑥验收截图、点交互、console
⑦回报改了什么、哪些是假设、偏差

「不要做的事」写成清单，它会照做；「适当发挥」这种话，每次理解都不一样。

起手模板 · 七段
① 角色：你是资深产品设计师兼前端工程师。 ② 背景：[这件事是什么、为什么做、给谁看；以哪份文档为准] ③ 输入：[你会拿到哪些材料，每份怎么用；互相冲突时以谁为准] ④ 不可妥协：[3–6 条硬规则，例如：文案逐字使用，不许润色；没定的信息留空，不许编；颜色、字号、圆角只用设计系统里的值] ⑤ 规格：[逐屏 / 逐段 / 逐个交互写清楚，用表格：段落 | 现状 | 你要做的] ⑥ 验收：[在 390 和 1440 两个宽度截图，逐项点交互，console 零报错] ⑦ 回报：改了什么；哪些是示例或假设；和要求的偏差；没完成的事。 不要做的事：[清单，例如：不要新增我没列的段落；不要换字体；不要加我没要的动效]
