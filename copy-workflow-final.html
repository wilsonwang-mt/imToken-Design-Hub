已确认的决策
以下三项作为最终方案的基本前提
DECISION 1

跳过 Crowdin

当前 3 种语言（EN / ZH-Hans / ZH-Hant）由团队内部完成翻译，无需 Crowdin。仅在语言扩展至 5+ 时再引入。

DECISION 2

开发先定义 i18n Key

开发在实现前端 V1 时定义 key 命名并生成初始 i18n 文件，设计师在此基础上创建 Figma Variables。

DECISION 3

设计初稿覆盖 80% 英文文案

设计师在产出设计稿时，同步与团队讨论并输出完成度 ~80% 的英文文案，作为开发 i18n 文件的初始内容。

02Developer

前端 V1 实现 + 定义 i18n Key

开发根据设计稿实现页面第一版，基于组件结构定义 i18n key 命名，生成初始英文 i18n JSON 文件（含设计师提供的英文文案）。

  • 完成后将 i18n 文件提交 GitHub，通知设计师

03Designer

导入 i18n → 创建 Figma Variable Collection

设计师拿到开发的 i18n 文件后，转换为 Figma 可导入格式，批量创建 Variable Collection（EN / ZH-Hans / ZH-Hant 三个 Mode），并用插件自动绑定文本图层。

  • 使用转换脚本将 dev i18n JSON → Variable Importer 插件格式
  • 导入后建立三语 Mode，补充中文翻译初稿
  • 用 Auto-Replace Text with Variables 批量绑定文本图层
  • 切换 Mode 预览各语言排版效果，提前发现溢出 / 截断问题
转换脚本Variable Importer/ExporterAuto-Replace Plugin
▶ How to: 如何将 i18n 文件导入 Figma 并绑定文本图层？

分三个阶段：A) 用转换脚本将 dev 的 i18n JSON 转为 Variable Importer 插件格式（含三语 Mode）；B) 在 Figma 中运行 Variable Importer/Exporter 插件批量创建 Variable Collection；C) 使用 Auto-Replace Text with Variables 插件自动匹配并绑定文本图层到对应 Variable。

04PM / Mkt / LegalDesigner

多方审查 & 定稿

产品经理、Marketing、安全/合规团队在 Figma 中审查三语文案。设计师根据反馈直接编辑 Variable 值，实时看到修改对 UI 的影响。

  • 审查人员通过 Figma Comment 标注需修改的文案
  • 设计师在 Variables Panel 中直接编辑值
  • 切换语言 Mode 让各方确认中文翻译准确性
  • 所有审查意见闭环后标记为"定稿 (Finalized)"

▶ How to: 多方审查流程如何组织？

05Designer

导出 → 转换 → 提交 GitHub PR

设计师从 Figma 导出 Variable Collection（三语 DTCG JSON），运行转换脚本生成 dev-ready i18n 文件 + Changelog，通过 GitHub 提交 PR。

  • PR 描述中附 Changelog 摘要，标注变更 key 数量和各语言修改项

开发 Review PR，确认 key 无冲突、格式正确，merge 到主分支完成上线。如有问题在 PR 中评论，设计师修改后再提交。

关键规则
团队执行此工作流时需遵守的约定

GitHub 是 Source of Truth

i18n JSON 文件以 GitHub 仓库为准。Figma 是编辑工具而非存储层，每次改动必须最终落到 Git commit。

Key 命名由开发主导

Key 是前端架构的一部分。开发定义后设计师导入使用，设计师不自行新增/删除 key，需通过开发操作。

每次 PR 必须附 Changelog

设计师提交 PR 时必须附三语 Diff 报告（Changelog），标注变更 key 数量、各语言 before/after。

长文本与短文案分治

UI 短文案（按钮、标题、提示）走 Figma Variables；HTML 富文本（FAQ、规则详情）走代码侧直接管理。

多语言 Mode 必须同步更新

在 Figma 中编辑任何 key 时，三语 Mode 必须同步更新，不允许只改一种语言而忽略其他语言。

文案定稿需 PM 签字

文案最终审批权在 PM。设计师编辑 Variable 后，需 PM 在 Figma Comment 中确认"Approved"方可导出。

Crowdin 引入条件
当以下任一条件满足时，考虑接入 Crowdin

Condition 1 — 语言数 ≥ 5

需要支持日语、韩语、西班牙语等团队不具备翻译能力的语言时，Crowdin 的专业翻译协作和 Translation Memory 才有显著价值。

Condition 2 — 外部翻译团队介入

当翻译工作外包给第三方翻译公司或自由翻译者时，需要 Crowdin 提供权限管理、翻译任务分配和质量审查。

Condition 3 — 持续迭代产品（非活动页）

从项目制活动页转向持续迭代的产品级应用时，Crowdin 的 GitHub 自动同步和增量翻译检测能显著降低持续维护成本。

架构兼容保障
当前方案的 i18n 文件格式（标准 JSON + namespace 规范）与 Crowdin 完全兼容。未来接入时只需配置 Crowdin ↔ GitHub Integration，无需改动现有文件结构。从 Direct Sync 切换到 Crowdin Pipeline 的迁移成本接近零。
